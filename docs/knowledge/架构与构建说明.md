# 音频框架架构与构建说明

## 分层模型

```text
应用 / JavaScript / C / CJ / Taihe
                 |
              框架绑定
                 |
             原生客户端
                 |
          IPC / 共享缓冲区边界
             |             |
         音频策略服务    音频流管理
             |             |
       设备/焦点/音量    流/端点/引擎
             \             /
              HDI 和插件
```

## 模块职责

- `interfaces/` 定义公共契约和数据类型。
- `frameworks/` 将公共 API 转换为原生客户端操作。
- `audio_policy` 决定操作是否允许、应该使用哪个设备以及如何协调多个流。
- `audio_stream` 表示音频流管理责任域，负责流对象、生命周期、缓冲区、端点和流执行操作；源码实现主要位于 `services/audio_service/`。
- `audio_engine` 提供处理节点、处理链和引擎扩展能力；`audio_suite` 承载可选音频编创能力。
- HDI、PulseAudio、蓝牙、USB 和分布式适配器负责连接具体设备实现。

知识库按以下五类组织主题，阅读时应以主题的责任域为准：

- `common`：跨模块公共机制、性能与内存、安全隐私和诊断。
- `audio_policy`：设备、路由、音量、会话、焦点策略和多音区等全局策略。
- `audio_stream`：音频流管理责任域，涵盖 Renderer、Capturer、sink/source 以及流通路执行。
- `audio_engine`：处理图、节点、插件和在线音效执行。
- `audio_suite`：可选音频编创能力及其服务协作。

## 构建入口

- `bundle.json` 声明组件、系统能力、依赖、功能开关、框架目标和服务目标。
- `config.gni` 定义低时延、分布式音频、内部采集、离线音效、USB 音频、OpenSL ES 和多音区等可选能力。
- `frameworks/js/` 和 `frameworks/native/` 提供不同语言与调用方式的框架入口。
- `services/audio_service/` 和 `services/audio_policy/` 分别承载音频流管理与全局音频策略。
- `sa_profile/` 管理系统能力的注册配置。

## 系统能力和 IPC

音频流管理和音频策略通过受控的进程间调用协作；代理端、服务端和接口描述共同定义跨服务数据边界。涉及跨进程行为时，应确认两端语义、身份传递、失败返回和生命周期一致。

## 参考来源和修改边界

| 内容 | 优先检查的参考来源 | 边界 |
| --- | --- | --- |
| 公共 API、类型和错误码 | `interfaces/` | 变更后同步原生客户端、多语言绑定、版本和测试 |
| IPC 协议 | `services/*/idl/`、代理、Stub | 两端同步修改，保持接口码和序列化顺序 |
| 构建目标和依赖 | 对应目录的 `BUILD.gn`、`bundle.json` | 不直接修改生成产物，不绕过条件依赖 |
| 功能开关 | `config.gni` 及相关 `.gni` | 明确默认值、依赖、关闭行为和降级路径 |
| 系统能力注册 | `sa_profile/`、服务入口 | 同时检查权限、生命周期和服务恢复 |
| 诊断事件 | `hisysevent.yaml`、对应 DFX 代码 | 不输出 PCM、令牌值、设备地址和未脱敏身份 |

当公共契约、实现行为和知识文档不一致时，以当前源码和构建配置为证据；不要把单一实现路径推断为稳定公共 API 契约。

## 功能开关规则

- 关闭功能开关后，不能破坏基础 Renderer、Capturer、策略和服务路径。
- 功能开关内的符号、依赖和行为不能无保护地泄漏到基础构建。
- 涉及设备、账户、分布式音频、电源或输入的功能，必须允许对应依赖不存在。
- 新增开关需要说明默认值、所属模块、依赖、降级行为和测试覆盖。

## 修改检查清单

1. 找到公共契约和内部接口。
2. 跟踪客户端代理、服务端 Stub 和服务实现。
3. 检查策略影响以及设备、流状态转换。
4. 检查功能开关、接口行为和依赖影响。
5. 补充正常路径、异常路径和服务不可用路径测试。

## 验证命令

构建命令从完整 OpenHarmony 源码根目录执行，不在 `multimedia_audio_framework` 子目录执行：

```sh
# 构建完整系统
./build.sh --product-name rk3568 --ccache --build-target make_all

# 只构建音频框架组件
./build.sh --product-name rk3568 --ccache --build-target audio_framework
```

验证步骤：

1. 读取变更目标所在目录的 `BUILD.gn`，确认目标名、依赖和测试目标。
2. 根据变更范围选择完整系统构建或 `audio_framework` 组件构建。
3. 执行对应单元测试、服务级测试或 `test/fuzztest/` 目标。
4. 执行 `git diff --check`，并复查接口、配置、日志和文档索引。
5. 若产品名、源码根目录或构建环境不同，记录实际使用的命令，不能将示例命令伪装成已执行结果。

## 完成标准

变更只有在源码、配置、接口兼容性、测试和文档影响均已检查，并且验证结果已记录时才算完成。无法执行构建或设备测试时，必须记录具体原因、已完成的替代检查和剩余风险。
