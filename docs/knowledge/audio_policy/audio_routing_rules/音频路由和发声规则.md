# 音频路由和发声规则

## 范围

本主题负责将设备能力与流用途、音频场景和发声规则结合，确定输入或输出会话应使用的目标设备及策略。设备本身的枚举与生命周期见“音频设备管理”；处理 pipe 选择见“通路选择”。

## 设计规格

### 发声规则概述
- 音频设备发声规则用于描述一个设备连接多个音频外设的情况下，默认选择那个设备出声或录音，推荐原则如下：
- - 用户选择手动优先
- - 隐私设备优先
- - 相同优先级设备后入优先
- 不同的场景可选择设备不同，比如通话场景优先隐私设备，同时要保证上下行一致；比如只有一个蓝牙音箱的场景，默认通话要选择本机听筒、MIC，但是媒体默认选择蓝牙音箱。
- 不同产品可能有不同的发声体验，因此需要根据产品体验配置不同的策略。

### 音频路由引擎
- 音频路由引擎体验模型，是面向用户体验的音频通路决策框架：
- 引擎采集系统、应用、设备三类上下文，自动完成信息收集、优先级排序、路由规则匹配、冲突仲裁，最终为每一条音频流（媒体、通话、铃声、录音等）输出最优输入 / 输出硬件设备，决定声音走哪条通路。
- 同时配套一套可量化的用户体验指标体系，用来评估路由决策好坏，把 “用户感觉好不好” 转化成可打分、可迭代的量化项（路由准确性、优先级合理性、隐私保护、切换流畅度、响应及时性）。

### 路由策略
- 音频路由整个决策框架为一个策略模式，包括多种策略，按优先级排序：应用强选路由策略 > 用户强选策略 > 隐私设备策略 > 公共设备策略 > 默认策略。
- 每个产品支持哪些路由策略也可以根据诉求配置在audio_strategy_router.xml中。
- 媒体跟随通话策略，这个特殊的策略是为了有些产品因为芯片约束同时只能有一个输入输出设备，优先保证通话业务。在通话过程中媒体默认跟随通话的设备路由选择结果；若产品支持同时从多个设备出声，通话和媒体可以走不同设备，可以不用支持该策略。
- PairDevice策略，成对设备策略，通话的听筒（输出）和麦克风（输入）必须来自同一个音频设备实例，不支持跨设备组合拾音 / 放音。它的主要目的是保障通话音频算法有效性：耳机 AEC、回声消除、降噪算法是基于耳机本地的麦 + 扬声器设计，一旦拆分设备，回声抑制算法失效，出现严重回声啸叫。
- 眼镜设备特殊策略：通常情况下隐私设备（蓝牙耳机、星闪耳机、有线耳机）接入或佩戴时会抢占当前发声的设备，但是眼镜比较特殊，可能用户扶一下眼镜可能就会触发一次用户摘下、佩戴事件出来，按默认隐私设备的策略就会抢占当前的发声设备。因此为保障体验的连贯性，眼镜首次连接佩戴，适用隐私设备后入优先原则自动切换出声。后续眼镜的摘下和佩戴，若发声的不是本机扬声器或听筒，不触发出声通路的自动切换。
- 来电铃声双响规格：在用户佩戴耳机来电时耳机与本机外放同时响铃，避免用户漏接来电，这里有个注意的地方，若设备支持佩戴检测，在耳机佩戴的情况下，只在耳机响铃，避免社死现象。

### 系统上下文

#### 系统强选
- 系统提供的UX支持用户选择输入、输出音频设备，它的作用域是全局，即全部应用；
- 当然系统UX可以支持按场景选择设备，比如为通话或媒体场景输出设备提供不同的UX入口。
- 系统强选是用户显式的、主动的强制意图，优先级高于自动路由策略、应用推荐路由。

#### 系统设置
- 系统音频的持久化偏好配置，属于默认策略参数。
- 本质用户提前预设的全局音频偏好，是自动路由规则的配置项，不是单次即时指令。
- 比如在系统设置菜单中提供设置项支持在连接车机的场景是使用系统默认策略还是优先走车机出声，满足不同用户差异化诉求。

#### 默认设备出声规则
- 默认设备出声规则，是音频路由引擎在没有用户实时强选（系统强选 / 应用强选） 时，预先定义的一套场景 + 流类型的设备选择基线。
- 比如通话场景隐私优先，来电铃声双向规格。

#### 默认拾音规则
- 音频路由引擎在不存在用户、应用的显式强选指令时，面向不同录音业务场景预设的麦克风基线选择策略。
- 核心思路是按音频流业务类型识别诉求，差异化匹配麦克风硬件与音频链路能力，不是所有录音都统一走同一个麦克风、同一条处理链路。
- 典型诉求差异：直播 / 录像侧重拾音音质、信噪比、采样规格；输入法语音输入（语音转文字）侧重低端到端时延；普通备忘录录音兼顾均衡；通话拾音侧重降噪与回声抑制。

#### 芯片平台约束
- 芯片平台约束，是路由引擎做音频通路决策时必须遵守的SoC/DSP 硬件底层能力限制，属于硬约束，优先级高于默认出声 / 拾音基线规则。即便上层业务、用户意图希望实现某一种路由方案，如果芯片 DSP、音频硬件架构不支持，路由引擎也不能生成超出硬件能力的决策，需要做方案降级、冲突仲裁。
- 典型限制：部分芯片平台音频 DSP 架构，同一音频方向（输入 / 输出）同一时刻仅支持一路物理通路，只能输出到一个设备，或者只能从一个麦克风设备拾取音频，无法并行分发到多个外设。
- 其他典型限制：高规格音频链路（多麦融合、高采样率）会占用大量 DSP 算力，带来功耗上升。平台会在低电量场景下，限制启用重型音频算法，路由引擎需要兼顾功耗约束做链路降级。
- 芯片平台约束属于底层硬限制：芯片平台约束 > 默认出声 / 拾音基线规则；但用户系统强选 / 应用强选仍然是最高业务指令：如果用户强选了一个硬件上不可达的路由目标，引擎不会无视用户指令，而是返回能力不支持，同时做可用兜底路由，并上报异常。

#### 短距链路约束
- 短距链路约束，是蓝牙、星闪（NearLink）这类短距无线音频链路带来的协议、带宽、链路状态层面的硬性限制，作为路由引擎决策的前置校验条件。即使设备已配对、硬件芯片支持，若短距协议本身不支持并发链路组合，路由引擎不能生成超出协议能力的路由方案，需要进入冲突仲裁、链路降级逻辑。
- 部分平台协议栈限制：两副蓝牙耳机、两副星闪耳机、一副星闪 + 一副蓝牙耳机，无法同时建立音频链路并行工作。
- 经典蓝牙协议原生限制：单个蓝牙耳机，不能同时维持 SCO 通话链路 + A2DP 媒体播放链路。
- 短距链路约束属于底层链路硬约束：短距链路约束 > 默认出声 / 拾音基线规则。与芯片平台约束并列，同属于系统上下文底层硬限制；但系统强选 / 应用强选优先级更高：如果用户强选了一个协议不支持的并发路由，引擎会识别链路不可达，返回能力受限，同时选择可用兜底路由，并上报链路约束异常。

### 应用上下文
#### 应用强选
- 应用强选，是应用侧发起、作用域限定于当前应用自身音频流的路由指定指令，优先级高于默认出声 / 拾音基线规则，它分为两大类：应用内 UX 用户选择、应用 API 主动配置偏好 / 默认设备。
- 应用内 UX，由用户在 App 界面选择本应用的输入 / 输出设备，和系统强选一样它也是用户的操作，其优先级和系统UX用户强选一致，后入生效，即以用户最后的操作为准。
- 应用开发者通过音频框架 API，在代码层面预先声明本应用业务偏好设备、默认设备。没有用户在 App 内手动点选，由业务本身的属性自动下发偏好。
- 偏好设置的优先级低于应用强选或系统强选。
- 应用设置默认设置只是覆盖系统默认的路由策略，不会修改优先级。

#### 流强选
- 流强选，是单条音频流维度的路由指定指令。区别于应用强选（作用域为整个 App），流强选可以对同一个应用内部不同音频流单独指定输入 / 输出设备，给应用提供更精细化、按流拆分的路由策略。
- 优先级：流强选 > 应用强选

#### 业务优先级
- 应用是否活跃、应用业务优先级（流类型）、应用前后台状态共同构成业务优先级决策输入集，用于路由引擎做多音频流并发冲突仲裁，判定多条流之间谁优先抢占拾音 / 播放硬件资源，同时决定低优先级业务的跟随策略。
- 应用业务优先级：业务类型自带的固有优先级基线，由系统预先定义业务等级。它描述业务本身的重要程度，和 App 在前台 / 后台无关；通话业务本身就是最高等级，无论 App 是否在前台。
- 应用前后台状态：标记应用是前台（用户当前正在交互）还是后台驻留。作为优先级微调因子。同业务类型下，前台 App > 后台 App；
- 应用是否活跃：标记应用当前是否处于用户有效会话激活状态，它根据应用的流状态来判定。

### 设备上下文
- ，描述当前所有已连接音频外设的实时状态、属性、能力与优先级。路由引擎在收集上下文阶段采集该组信息，用于设备筛选、路由匹配、冲突仲裁，支撑出声 / 拾音决策。包含 5 个子项：设备状态 (用户操作)、设备佩戴 (用户操作)、设备属性 (隐私 / 公共)、设备音频能力、设备优先级。

#### 设备状态(用户操作)
- 反映由用户操作触发的音频设备连接 / 断开、插拔、配对、手动断连等实时状态。属于设备的基础在线状态。
- 典型事件：插入有线耳机、拔出耳机、蓝牙耳机配对连接、用户在设置面板断开蓝牙音频设备、设备重连。
- 设备状态发生变更，触发路由重决策，重新评估当前所有活跃音频流的通路。
- 设备佩戴(用户操作) ：针对支持佩戴检测的无线耳机（TWS、头戴星闪 / 蓝牙耳机），采集用户是否佩戴耳机的感知状态，属于用户使用意图的补充信号。由设备传感器上报，反映用户当前是否正在使用该耳机。佩戴状态作为设备可用性的附加判断条件。区分「链路连上」和「用户正在佩戴使用」，减少无效路由。提升路由准确性，避免声音送到已连接但摘下闲置的耳机。
- 耳机多连接状态：一副蓝牙耳机同时配对、连接两台手机 / 平板。耳机可以在两台主机之间切换音频流，但同一时刻只能接收其中一台主机的音频；该能力是耳机端特性，并非手机主机侧多输出。从主设备侧感知到的是耳机可用或不可用状态。

#### 设备属性(隐私/公共)
- 对音频设备做属性标签分类，分为隐私设备和公共设备，是路由引擎隐私保护规则的核心输入。
- 隐私设备：有线耳机、TWS 蓝牙耳机、头戴星闪耳机；声音仅佩戴者可收听，麦克风采集仅近距离人声。
- 公共设备：本机扬声器、外接公共音箱；声音向外扩散，周围人可以听见，存在音频外泄风险。

#### 设备音频能力
- 述当前音频设备硬件 + 协议栈支持的音频能力集合，作为路由方案可行性校验依据。包含：
- 播放能力：支持的音频编码（LC3/A2DP）、采样率、位深、最大声道；
- 拾音能力：是否支持多麦阵列、降噪、回声消除、高清录音；
- 链路类型：蓝牙 SCO/A2DP、星闪音频、有线 I2S；
- 在路由决策后做可行性校验，业务诉求必须匹配设备音频能力。
- 例：直播业务需要 48kHz 高清拾音；选中的蓝牙麦仅支持 16kHz，引擎判定能力不匹配，自动降级到符合能力的备选麦克风。
- 例：普通 A2DP 耳机不支持 SCO 通话链路，不可作为通话输出设备。

#### 设备优先级
- 同类型多个可用设备在线时，系统预先定义的设备优选顺序基线。属于静态配置，可叠加用户历史使用偏好微调。

### 音频路由决策
- 音频路由决策输出，是路由引擎将前面多维度上下文（系统、应用、设备上下文）、强选指令、业务优先级、硬件 / 链路约束综合仲裁得到的路由结论，翻译成标准化通路配置指令，下发至音频服务、协议栈、DSP 驱动；同时向上层业务、系统反馈路由结果，处理执行失败兜底，持久化必要用户偏好。
- 路由决策大致流程：
- - 先搜集所有流
- - 执行一遍路由策略，做一次设备预选，用于冲突检测
- - 再针对每条流执行路由策略，同时校验是否有冲突
- - 最后根据选择的结果执行通路选择流程
- 通常输入与输出选择的结果不是孤立的，也可能发生冲突，因此建议每次触发路由输入、输出都要一起选。


## 约束与常见误区

- 不同场景下的输入和输出规则可能不同，不能依据设备类型单独推导最终路由。
- 首选设备是策略输入，不是绕过权限、设备可用性、格式能力或隐私限制的强制命令。
- 设备切换期间需协调活动流、音量、焦点、通路和端点状态，避免旧路由残留或短暂错误发声。
- DTMF 和强制提示音受场景和权限限制，不能按普通媒体流开放。
- 不把策略配置中的单一规则当作所有产品、账户和音频场景的普遍保证。

## 安全与隐私

- 路由请求需校验调用者身份、设备控制权限、UID/会话归属和远端授权。
- 录音设备选择必须遵守麦克风权限、隐私开关和设备封锁状态。
- 不向应用泄露其他应用的路由、会话或设备偏好；日志不输出原始地址或网络标识。
