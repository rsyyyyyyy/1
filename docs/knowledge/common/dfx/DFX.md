# DFX

## 范围

DFX 描述音频框架公共诊断机制和关键观测点，包括结构化日志、系统事件、调用跟踪、状态转储、音频转储和异常恢复观测。模块文档关注何时观测、观测什么和数据边界，不规定具体代码写法。

## 设计规格

- 通过统一诊断机制呈现客户端、策略、服务、引擎和设备适配层的重要状态变化。
- 关键观测覆盖会话创建与释放、焦点和路由变化、设备连接状态、pipe 与处理链建立、服务异常和恢复结果。
- 指标和事件应能关联同一操作或会话，同时避免跨会话混淆。
- 跟踪能力可受构建或运行配置控制；诊断能力关闭时基础业务不应受影响。
- 转储应具备明确的授权、触发、范围、存放和清理策略。

## 约束与常见误区

- 诊断事件应表达可操作状态，不以高频、重复或含糊日志代替状态定义。
- 日志不等同于事实来源；排查时应与返回状态、系统事件和服务状态交叉验证。
- 不要把诊断开关默认开启或关闭写成跨产品保证。
- 采样、限频、大小上限和异常路径必须考虑，避免诊断本身造成实时音频阻塞。
- DFX 证据不得替代权限检查或业务状态校验。

## 安全与隐私

- 禁止记录 PCM、麦克风内容、原始令牌、设备地址、未脱敏应用身份和不必要的会话数据。
- 受控转储须校验调用方权限、用户同意和生命周期，并限制数据规模和保留时间。
- 诊断字段遵循最小化原则，对身份和远端信息使用受控、脱敏表示。
