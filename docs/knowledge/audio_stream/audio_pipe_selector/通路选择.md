# 通路选择

## 范围

通路，代码中用pipe表示，描述完整的数据传输通道。对于播放，包含从音频播放流获取数据，对数据进行重采样、格式转换、音效等处理，最后通过HDI接口输出到HAL的过程；对于录音，包含通过HDI接口从HAL获取录音数据，经过数据处理传入音频录制流的过程。

通路选择负责在音频流管理和策略协同范围内，为会话确定适用的处理 pipe，并协调 pipe 的建立、复用、切换和并发访问。它关注处理通路而非最终物理设备选择；设备路由见“音频路由和发声规则”。

## 设计规格

- 每个通路，应当可以通过其所关联HAL类型(AdapterType)和通路标识(RouteFlag)唯一确定。
- hdiadapter 内的 sink 和 source，是每个通路中调用 HDI 接口的模块，sink 对应播放，source 对应录制。
- 通过 HdiIdType 和 HdiIdInfo(以HDI_ID_INFO开头的宏定义) 获取指定通路的 sink 或 source 实例。但需要注意，HdiIdType 和 HdiIdInfo 当前都混合了关联HAL类型和通路标识信息，HDI_ID_TYPE_PRIMARY 并不表示此 sink 或 source 归属Primary HAL，而 HDI_ID_TYPE_PRIMARY + HDI_ID_INFO_DEFAULT 才对应Primary HAL的普通通路。
- 根据流方向、用途、音频场景、格式、时延目标、设备能力和产品配置选择通路。
- pipe 可承载数据处理、端点连接及相关资源；选择结果需与流生命周期和引擎处理能力相容。
- 当多个会话竞争共享 pipe、设备端点或处理资源时，应执行一致的并发协调，避免冲突启动、重复释放和状态覆盖。
- pipe 不可用或能力不匹配时，应选择受支持的替代通路或按既有错误语义失败。
- 配置和可选能力改变后，受影响的会话应按受控流程重建或迁移。
- 通路选择的正向流程依赖关系为 RendererInServer/CapturerInServer（流状态切换触发通路选择）-> AudioCoreService（确定通路选择策略）-> AudioServer（执行选择结果）-> HpaeManager（打开、关闭、重建或迁移流）/HdiAdapterManager（打开或关闭 HDI sink/source）。应避免反向调用引起 AudioCoreService::EventEntry 内 eventMutex_ 相关死锁。

## 约束与常见误区

- 不要把 pipe 选择、设备路由、焦点决策和音频引擎节点选择视为同一件事；它们可能相互影响，但职责不同。
- 并发锁、资源所有权和会话状态必须覆盖建立、迁移、失败回滚和释放全过程。
- 不可仅根据单一流属性选择通路；还需考虑方向、产品能力、设备能力及当前资源状态。
- 共享 pipe 的复用必须验证参数兼容和生命周期；不能让一个会话释放另一会话仍在使用的资源。
- 条件能力关闭、配置缺失或设备变化时须有定义明确的降级路径。

## 安全与隐私

- pipe 选择输入需校验枚举、格式、会话标识和调用权限。
- 并发失败不能导致跨会话数据串用、旧缓冲区复用或未授权通路访问。
- 诊断只记录通路类别和必要状态，不输出原始音频、令牌或敏感设备标识。

## 待改进点

- 调整 HdiIdType 和 HdiIdInfo 定义，按照通路设计规格，使用所关联HAL类型(AdapterType)和通路标识(RouteFlag)唯一确定替代。
- 铃声双响通过音频引擎新增分流节点能力实现，避免在通路选择执行过程中直接创建音频播放流。
