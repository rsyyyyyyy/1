# 音频焦点管理

## 范围

焦点概念说明：音频焦点指多个应用同时申请播放/录制时，系统决定资源分配给谁，获得资源的应用即持有焦点。多个应用并发申请焦点时，系统按一套焦点打断（interrupt）策略仲裁谁能获取焦点。因此焦点相关代码中大量使用 interrupt 命名，interrupt 即指焦点。
本主题描述音频框架基础焦点策略的组成、申请与释放流程、并发仲裁规则以及常见响应动作。焦点是会话协调的子能力之一，只回答“谁可以发声、谁应该让位、如何让位”的策略问题，不涉及会话生命周期编排和 AudioSession 应用级焦点与策略影响能力。会话层面的激活、属性、超时与跨会话协调见 [音频会话.md](../audio_session/音频会话.md)，跨音区焦点同步和分布式焦点注入见 [音频多音区.md](../audio_multi_zone/音频多音区.md)。

## 设计规格

### 焦点模型

- 焦点按音区维护，每个音区拥有独立的焦点栈；默认仅主音区。
- 每个焦点条目关联流 ID、流类型、应用身份、来源类型和会话标识。
- 同一音区中允许存在多个活动焦点，由策略决定共存、闪避、暂停、停止或静音。
- 焦点状态分为活动、挂起、暂停等，状态转换由焦点服务统一维护，外部只能通过受控接口触发。

### 接口分层

- 焦点接口分为旧版与新版两套：旧版按客户端 ID 维护，新版按流 ID 和音区 ID 维护。
- 新增策略或修改行为时，必须确认两套接口的行为一致性，并在旧版路径上保留既有兼容语义，不强行迁移到新版契约。
- 抢占模式、闪避直通和闪避系数调整属于影响后续焦点策略执行结果的辅助能力，调用前需确认调用方权限和适用范围。

### 策略组成

基础焦点策略按当前焦点与申请焦点的组合分发到不同子策略，常见类别包括：

- 静音让位：对申请方执行静音，常用于隐私或不可打断场景。
- 窗口焦点：结合应用前台/后台状态判定优先级。
- PC 模式：PC 形态下的特殊优先级与并发规则。PC 与手机、平板等产品的基础焦点策略不同，因此 PC 的基础焦点策略单独维护。
- 暂停让位：让位方进入暂停状态，并按超时阈值触发回收。该策略用于解决短时被其他媒体打断后无法自动恢复的问题；对于长时打断场景，不会再触发恢复动作，此时彻底停止效果更好。

公共契约映射：应用通过会话策略声明的并发模式（默认、与其他混播 MIX_WITH_OTHERS、闪避其他 DUCK_OTHERS、暂停其他 PAUSE_OTHERS，@since 12）决定让位语义——混播模式允许共存，闪避/暂停模式对应内部闪避让位/暂停让位策略。应用声明的行为标志（中断时静音 MUTE_WHEN_INTERRUPTED、中断时暂停 PAUSE_WHEN_INTERRUPTED，@since 24）对应内部静音让位/暂停让位策略；标志为空表示清除设置，不改变既有行为。

### 响应动作

- 焦点策略产生的响应动作下发到对应流，对应公共状态提示：恢复、暂停、停止、超时停止（TIME_OUT_STOP，@since 20）、闪避（DUCK）、取消闪避（UNDUCK）、静音建议（MUTE_SUGGESTION，@since 23）、取消静音建议（UNMUTE_SUGGESTION，@since 23）、静音（MUTE，@since 24）、取消静音（UNMUTE，@since 24）。
- 静音建议与强制静音不同：建议由应用自行决定是否执行，强制静音由系统直接生效。混播模式下默认不下发静音，仅当应用启用静音建议后才下发建议提示（@since 23）。
- 闪避系数有默认值，可由独立接口调整；直通场景可绕过框架侧闪避，主要用于部分产品自行定制闪避系数的情况。
- 让位流可进入挂起状态，并由独立接口通知与回填状态。
- 让位方进入暂停后由超时监控机制管理，超过阈值未恢复则触发清理。

### 焦点查询

- 查询当前持有焦点的流或会话信息，用于策略决策和诊断。
- 按音区或音区+设备标记查询焦点列表，用于分布式多投一场景的对端同步。
- 校验流或会话当前是否处于活动焦点状态，供其他模块判断是否可以发声或录音。

### 音区与外部协同

- 焦点音区的创建、释放与迁移由焦点服务管理，行为详见 [音频多音区.md](../audio_policy/audio_multi_zone/音频多音区.md)。
- 分布式焦点注入、暂停与恢复用于跨设备焦点同步，必须由具备分布式权限的调用方发起。
- 系统休眠与唤醒会触发焦点重评估；独立模式下焦点按音区隔离。

### 调试与诊断

- 焦点申请、释放、让位事件及响应结果由诊断机制记录，供问题定位。
- 焦点栈和会话状态提供转储入口，便于排查策略路径。
- 诊断字段不含 PCM、令牌值或设备地址；日志仅记录流类型、会话标识和响应结果类别。

## 约束与常见误区

- 焦点申请成功不等于流已实际发声或设备已选定；流状态、路由状态和端点状态需独立确认，见 [音频播放.md](../../audio_stream/audio_renderer/音频播放.md) 和 [音频路由和发声规则.md](../audio_routing_rules/音频路由和发声规则.md)。
- 焦点策略属于全局协调层，单一应用的请求可能影响其他应用的流；新增策略时必须同时评估对其他流的副作用，避免确定性或公平性问题。
- 旧版接口和新版接口不得在同一调用链路混用；旧版接口的行为不能因新版策略调整而无声地改变。
- 焦点服务持有焦点栈和回调映射，新增接口或回调时必须保证回调注销、服务死亡和远端对象失效路径不产生悬空引用或重复回调。
- 让位动作下发是异步的，调用方不能假设焦点策略执行后立即生效；需要等待事件分发回调完成才能确认最终状态。
- 新增子策略必须明确：触发条件、作用域（全局/音区/UID/流）、对当前焦点和申请方焦点的副作用、降级路径；不得把某一产品或场景的策略写成所有产品的通用契约。
- 焦点策略中的超时阈值、闪避系数和延迟参数属于策略参数，变更需评估时延、并发和体验影响，不视作公共 API 契约。

## 安全与隐私

- 焦点申请与释放需校验调用方身份、UID/PID、会话归属和流用途；特殊流类型（通话、VoIP、AI、地图、录音）走专用策略分支，权限不足时拒绝。
- 焦点申请入口执行权限校验；客户端传入的身份不可信，必须以服务端校验结果为准。
- 焦点查询接口只返回调用方有权知晓的流和会话信息；不得跨应用泄露其他应用的焦点状态、应用包名或会话标识。
- 分布式焦点注入必须验证远端授权和当前可信状态，未授权的注入请求应失败关闭并保留原焦点栈。
- 诊断和转储不得输出原始 PCM、令牌值、设备地址或未脱敏的应用包名；焦点调试信息仅记录策略路径和响应类别。
