# 音频框架架构与构建说明

## 分层模型

```text
应用 / JavaScript / C / CJ / Taihe
                 |
              框架绑定
                 |
             原生客户端
                 |
          IPC / 共享缓冲区边界
             |             |
         音频策略服务    音频服务
             |             |
       设备/焦点/音量    流/端点/引擎
             \             /
              HDI 和插件
```

## 模块职责

- `interfaces/` 定义公共契约和数据类型。
- `frameworks/` 将公共 API 转换为原生客户端操作。
- `audio_policy` 决定操作是否允许、应该使用哪个设备以及如何协调多个流。
- `audio_service` 管理流对象、生命周期、缓冲区、端点和服务端音频操作。
- `audio_engine` 提供处理节点、处理链和引擎扩展能力。
- HDI、PulseAudio、蓝牙、USB 和分布式适配器负责连接具体设备实现。

## 构建入口

- `bundle.json` 声明组件、系统能力、依赖、功能开关、框架目标和服务目标。
- `config.gni` 定义低时延、分布式音频、内部采集、离线音效、USB 音频、OpenSL ES 和多音区等可选能力。
- `frameworks/js/napi:audio` 构建 JavaScript 绑定。
- `frameworks/native/ohaudio:ohaudio` 构建 C API。
- `services/audio_service:audio_service_packages` 构建音频服务。
- `services/audio_policy:audio_policy_packages` 构建音频策略服务。
- `sa_profile:audio_service_sa_profile` 打包系统能力配置。

## 系统能力和 IPC

`AudioServer` 是系统能力并实现标准音频服务 Stub。策略侧代理通过系统能力管理器获取音频服务远程对象。音频策略和音频服务分别维护 IDL、代理和 Stub；序列化顺序及接口码属于兼容性契约。

## 功能开关规则

- 关闭功能开关后，不能破坏基础 Renderer、Capturer、策略和服务路径。
- 功能开关内的符号、依赖和行为不能无保护地泄漏到基础构建。
- 涉及设备、账户、分布式音频、电源或输入的功能，必须允许对应依赖不存在。
- 新增开关需要说明默认值、所属模块、依赖、降级行为和测试覆盖。

## 修改检查清单

1. 找到公共契约和内部接口。
2. 跟踪客户端代理、服务端 Stub 和服务实现。
3. 检查策略影响以及设备、流状态转换。
4. 检查功能开关、ABI 和依赖影响。
5. 补充正常路径、异常路径和服务不可用路径测试。
